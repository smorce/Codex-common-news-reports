## 【RAG】話題の米国AIベンチャーで実践される「社内ナレッジ」管理
- Date: 2026-08-04T00:00:00+09:00

### Executive Summary
- Cerebras の社内ナレッジ基盤を題材に、実運用されている RAG 型検索の構成を解説している。
- リリースから 3 か月で 1 日 15,000 件以上の質問に回答している点が、机上論ではない事例として強調されている。
- Pinecone などの専用ベクトル DB ではなく、Postgres、GIN インデックス、pgvector を中心に構成している。
- Slack スレッドはそのまま埋め込まず、LLM で構造化・要約・想定質問化してから検索用データに変換している。
- 長いスレッドでは、同一人物の連続発言を条件付きで切り出し、重要発言が埋もれないようにしている。
- 検索時はキーワード検索、ベクトル検索、IDF、情報鮮度を並列に使い、RRF とリランカーで統合する。
- MCP では検索部品をツールとして公開し、どの順で呼ぶかはエージェント側に任せる設計になっている。
- 一方で、自前 DB に同期する方式では部署別アクセス権などの権限管理が大きな課題になる。

### Key Findings
- Cerebras Knowledge は既に大規模に利用されている運用事例である。 [^]
  - Footnote: 記事は、リリースから3ヶ月で「1日15,000件以上の質問」に回答し、人間だけでなく自動化システムやAIエージェントも質問していると説明している。
- 検索基盤は専用ベクトル DB に依存せず、Postgres に集約されている。 [^]
  - Footnote: 記事は「専用のベクトルDBを、一切使っていない」こと、キーワード検索は Postgres の GIN、ベクトル検索は pgvector で扱うことを述べている。
- Slack の生データは RAG に向きにくく、前処理が重要である。 [^]
  - Footnote: 記事は Slack の会話のような非構造データは素朴なベクトル検索だけでは精度が出ず、短文が詳細なメッセージに勝つことが多いと説明している。
- Slack スレッドは構造化されたドキュメントに変換してから保存される。 [^]
  - Footnote: 記事は、スレッド全体を LLM に読ませ、検索されそうな質問や短い要約データに変換してからベクトル化し DB に入れると説明している。
- 長いスレッドでは重要発言の埋没を避けるため、追加のチャンク化を行う。 [^]
  - Footnote: 記事は、同一人物の連続発言が一定条件を満たす場合、それも切り出して一つのチャンクとしてベクトル化すると述べている。
- 検索は複数手法を並列に使って弱点を補完している。 [^]
  - Footnote: 記事は、キーワード検索、ベクトル検索、IDF、情報鮮度の4つを並列で走らせ、それぞれの弱点を補うと説明している。
- ランキング統合には RRF と小型リランカーを使う。 [^]
  - Footnote: 記事は、各手法のランキングを RRF で統合し、最後に小型のリランカーモデルで上位10件に絞ると述べている。
- MCP には回答生成 API ではなく検索部品を公開している。 [^]
  - Footnote: 記事は MCP 経由では「この質問に答えて」ではなく、search_slack や search_code のような検索の部品をツールとして公開していると説明している。
- 自前同期方式では権限管理が最大の課題になりやすい。 [^]
  - Footnote: 記事は、経営幹部の Slack を一般社員が検索できてはいけない例を挙げ、誰がどのデータにアクセスできるかを自分たちで管理する必要があると述べている。

## プロンプトエンジニアリングのすすめかた
- Date: 2026-08-04T00:00:00+09:00

### Executive Summary
- プロンプトエンジニアリングを文章術ではなく、評価と計測の仕組み作りとして捉える記事である。
- TAKT の内部エージェントがモデル性能向上に伴って修正ループを起こした経験が導入になっている。
- 雰囲気でプロンプトを直すと、見落とし低減と誤検知増加のような回帰を見逃しやすいと指摘している。
- 実運用で観測したミスを再現可能な評価ケースに落とし、まず赤を確認する流れを重視している。
- promptfoo を使い、プロンプト、テストケース、アサーションを YAML で書いて pass/fail を判定する。
- LLM as a Judge は、形式ではなく実質を判定するようルーブリックを設計し、fail 条件も明示する。
- プロンプト修正はファセット単位で責務を特定し、最小差分で行う方針が示されている。
- 修正後は repeat 実行と他スイートの回帰確認を行い、ケースは再発防止の資産として残す。

### Key Findings
- プロンプト修正は計測結果で評価すべきである。 [^]
  - Footnote: 記事は「プロンプトが良くなった」は感想ではなく計測結果であるべきで、計測していない修正はテストのないリファクタリングと同じだと述べている。
- promptfoo によりプロンプト評価をスイート化している。 [^]
  - Footnote: 記事は promptfoo を LLM 出力の実験ツールと説明し、プロンプト、テストケース、合否基準を YAML で書くと pass/fail を判定できるとしている。
- TAKT ではプロンプト評価スイートが工程別に多数存在する。 [^]
  - Footnote: 記事は、レビュー・計画・修正・裁定といったステップごとにスイートがあり、現時点で20個以上あると述べている。
- 評価ケースは実運用のミスから作るべきである。 [^]
  - Footnote: 記事は、評価ケースを机上で発明するのではなく、実際に起きたミスから作ると説明している。
- 同族欠陥を一括で検出できない問題を評価ケース化している。 [^]
  - Footnote: 記事は、同じ種類の欠陥が7ファイルにあり、レビュアーが1箇所ずつ指摘してループが7往復する例を挙げている。
- LLM 採点では形式ではなく実質を判定させる必要がある。 [^]
  - Footnote: 記事は、見出しや表の形ではなく実質的な網羅で判定し、問題ファミリー全体を指摘した場合のみ pass とするルーブリック例を示している。
- 赤を確認することが修正効果測定の前提になる。 [^]
  - Footnote: 記事は、評価が最初から通るなら実際のミスを捉えていないため、プロンプトを触る前にケースを作り直すべきだと述べている。
- 修正はプロンプト部品の責務を特定して最小差分で行う。 [^]
  - Footnote: 記事は、TAKT のプロンプトはペルソナ、ポリシー、ナレッジ、インストラクションのファセットに分かれ、責務を特定して差分を入れると説明している。
- LLM の確率性に対応するため反復実行と回帰確認が必要である。 [^]
  - Footnote: 記事は、1回の緑は信用せず重要な修正は --repeat 3 で回し、クリーンな diff のケースも使って誤検知増加を確認すると述べている。
- 評価ケースは消さずに回帰テスト資産として残す。 [^]
  - Footnote: 記事は、緑になったケースには実際のミス、状況設定、効いた修正が残り、次の改善や回帰チェックに使えると説明している。

## Microsoft 謹製 デスクトップアプリ「Skill Recorder」で業務効率化スキル（SKILL.md）の作成が捗る？
- Date: 2026-08-04T00:00:00+09:00

### Executive Summary
- Microsoft の Skill Recorder を使い、PC 操作録画から SKILL.md を作成する流れを紹介している。
- 画面録画と音声実況を同時に取得し、業務の意図と手順を AI が言語化する点が中心である。
- ブラウザ操作だけでなく、ローカル PC アプリ操作ベースの業務棚卸しを狙っている。
- 前提として Node.js 24 以降、GitHub Copilot 権限付き GitHub アカウント、Windows 11 または macOS が必要になる。
- 録画・画面フレーム抽出・Whisper 文字起こしはローカル PC 上で行われると説明されている。
- Analyze 後に CREATE SKILL 画面で手順を編集し、Scout skill などの成果物形式を選んで出力する。
- 実用面では Microsoft 365 連携が重要で、筆者の試用でも Microsoft 365 が前提として示された。
- 機密情報を録画しないこと、業務利用では Copilot Business / Enterprise を推奨することが注意点として挙げられている。

### Key Findings
- Skill Recorder は画面操作と音声解説から SKILL.md を作るツールである。 [^]
  - Footnote: 記事は、PC画面での操作録画と音声解説から定型業務を言語化し、AIエージェント用スキル（SKILL.md）を簡単に作れると説明している。
- 業務棚卸しの負担と個人差を下げる狙いがある。 [^]
  - Footnote: 記事は、各個人の業務の言語化・構造化の負担と言語化精度の個人差を課題とし、録画と実況だけで再利用可能なスキルへ変換できると述べている。
- 録画と文字起こしはローカルファーストで処理される。 [^]
  - Footnote: 記事は、録画、画面フレーム抽出、音声文字起こし（Whisper）はすべてユーザーのローカル PC 上で行われると説明している。
- 出力は単なる座標再生マクロではなく、AI が実行可能な汎用スキルである。 [^]
  - Footnote: 記事は、UI の絶対座標を連打するマクロではなく、CLI、Web API、検索ツールなどを使う汎用形式（SKILL.md）として書き出すと述べている。
- 利用には Node.js 24 と GitHub Copilot 権限が必要である。 [^]
  - Footnote: 記事は前提条件として、GitHub Copilot へのアクセス権がある GitHub アカウントと Node.js 24 以降を挙げている。
- Windows では Windows 11 が前提で、スタートメニューから起動できる。 [^]
  - Footnote: 記事は Windows の前提条件を Windows 11（x64 または ARM64）とし、インストール後はスタートメニューのショートカットから起動すると説明している。
- 録画はショートカットまたは UI ボタンで開始できる。 [^]
  - Footnote: 記事は、Mac は ⌘ + Shift + R、Windows は Ctrl + Shift + R、またはアプリ画面の Record ボタンで録画開始できると述べている。
- Analyze 後に手順を編集して成果物形式を選ぶ流れである。 [^]
  - Footnote: 記事は、録画停止後に Analyze を押すと CREATE SKILL 画面が出て、ステップ編集後に Scout skill、Scout automation、Cowork skill などを選ぶと説明している。
- 本格利用では Microsoft 365 が重要な制約になる。 [^]
  - Footnote: 記事は、Skill Recorder を十分に活用するには Microsoft 365 が必要で、筆者の試用でも Microsoft 365 連携ツールが前提だったと述べている。
- 機密情報と学習利用の扱いに注意が必要である。 [^]
  - Footnote: 記事は、録画画面やテキストにパスワード、APIキー、個人情報、機密情報が含まれないよう注意し、業務利用では Copilot Business / Enterprise 契約下を推奨している。
